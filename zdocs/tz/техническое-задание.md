# ТЗ: автоматизированная система P2P-арбитража (крипто)

Nov 13, 2026 · @Valeru

## 1. Цели, границы и принятые решения

Система находит арбитражные связки на одной P2P-площадке, готовит сделки и ведёт учёт. Денежные шаги на бирже выполняются только после подтверждения оператора в Telegram Mini App. Фиатная оплата — всегда вручную: перевод на карту / по реквизитам из ордера.

**Принятые решения:**

- Площадка MVP: **Bybit**. Аккаунт есть, статус **General Advertiser** подтверждён. Осталось создать API-ключ с P2P read/trade **без** withdraw и привязать IP. Вторая площадка — после стабильного live. В MVP — только адаптер Bybit.
- Автоматизация: **полуавтомат**. Система ищет связки, готовит ордера, показывает реквизиты, ведёт чат с контрагентом в Mini App, помогает сверить поступление и учёт. Шаги на бирже (создание ордера, `mark_paid`, release) — только после подтверждения оператора. На старте все денежные шаги с `require_ack=true`.
- **Связка:** taker на Bybit P2P — купить USDT дешевле по одному объявлению → продать дороже по другому **в той же фиат-валюте**.
- Оплата фиатом: **только вручную**, всеми доступными на Bybit **методами перевода** (карты, СБП и прочие transfer-методы, которые отдаёт API для выбранной валюты). Банковского API нет.
- Валюты: **USDT** ↔ **RUB, EUR, USD, KZT**. Пары включаются в конфиге. Кросс-фиат (RUB→EUR) вне MVP.
- Карты / реквизиты оператора: **не только личные**; пул карт/счетов в т.ч. **казахстанские, грузинские, таджикские, узбекские, киргизские** (и другие по мере появления). Учёт инструментов в справочнике системы.
- Доказательство оплаты: **фото чека / скрин перевода обязательно** перед `mark_paid` и при подтверждении входящего платежа.
- Чат с контрагентом: **в Mini App** (чтение/отправка через Bybit P2P chat API, если доступен ключу).
- TTL подтверждений: **пока открыт** — в конфиге, значение уточняется на практике (см. §2).
- Масштаб: один оператор, один набор аккаунтов Bybit, без мультипользовательского режима.
- Интерфейс: **Telegram Mini App** — основной UI (сделки, реквизиты, чеки, чат, подтверждения). Бот — уведомления и быстрые команды.

**Режимы работы (лестница, переход вверх только вручную):**

| Режим | Что делает система | Деньги |
| --- | --- | --- |
| `dry-run` | Тянет объявления, считает маржу, пишет логи; ордера на биржу **не** создаёт; подтверждения не запрашивает | Нет |
| `paper` | Полный цикл сделки на **симуляторе** биржи; оператор подтверждает шаги в Mini App как в бою | Нет реальных |
| `live+confirm` | Реальные ордера на Bybit; каждый денежный шаг ждёт оператора; фиат — ручной перевод | Реальные, малые лимиты |
| `live` (позже) | То же, но отдельные шаги можно перевести в авто по флагу конфига | Реальные |

**Целевые показатели:**

- Чистая маржа сделки после всех комиссий не ниже порога из конфига.
- От появления связки до карточки подтверждения в Mini App: единицы секунд; дальше скорость задаёт оператор.
- Ноль выпусков крипты без `payment_matched` (оператор подтвердил входящий платёж) и без `operator_ack` на шаг release, пока для release не включён авто-режим.

**Вне границ MVP:** вторая биржа, maker-стратегия, банковский API / автооплата, спот-HFT, DeFi, обход KYC и правил площадок, SaaS, веб-панель вне Telegram, мобильное приложение. ИИ-агенты в MVP не входят; точка подключения закладывается (раздел 12).

## 3. Риски

Главный риск — рассинхрон «фиат ушёл / пришёл, а система или биржа об этом не знают». Подтверждение оператора снижает риск, но не заменяет сверку и лимиты.

| Риск | Что может случиться | Мера в системе |
| --- | --- | --- |
| Блокировка карт / счетов | Антифрод на частые P2P-переводы, в т.ч. по картам разных стран | Лимиты на сумму/частоту **по каждому** `payment_instrument`; ротация; учёт страны карты |
| Мошенничество контрагента | Платёж от третьего лица, chargeback, ложный спор | Release только после чека + `payment_matched` + `operator_ack`; чат и споры в Mini App; чёрный список |
| Риски пула чужих карт | Ошибка реквизита, спор «кто должен был принять», утечка данных карт | Справочник инструментов, маскирование в UI/логах, чек привязан к deal_id, доступ только whitelist оператора |
| Ограничение аккаунта Bybit | Бан за нарушение правил / злоупотребление API | Только официальный API, rate limits, ключи без вывода |
| Ценовой риск | Курс ушёл между ногами | TTL связки, буфер маржи, пересчёт перед шагом, отмена при потере выгоды |
| Латентность оператора | Пока ждём подтверждение, объявление/ордер протух | Таймер в карточке Mini App, перепроверка цены, автоотмена до оплаты |
| Сбой посреди сделки | Деньги отправлены, статус неизвестен | FSM в PostgreSQL, идемпотентность, сверка с Bybit, kill switch |
| Утечка ключей | Потеря средств | IP whitelist, секреты вне репо, минимальные права |
| Изменение API | Ломается логика | Адаптер за протоколом, контрактные тесты, алерты на аномалии |

## 4. Функциональные требования

Десять модулей; каждый проверяется на приёмке.

**FR-1. Сбор рыночных данных**

- Периодически получать объявления P2P Bybit по **включённым в конфиге** парам (`USDT/RUB`, `USDT/EUR`, `USDT/USD`, `USDT/KZT`).
- Методы оплаты: все **transfer**-методы, которые Bybit отдаёт для валюты; в конфиге — optional allowlist/denylist (например отключить не-переводы).
- Хранить срезы для истории и бэктеста.
- Соблюдать rate limits; backoff; опрос валют через очередь, чтобы не упираться в лимиты.

**FR-2. Поиск возможностей**

- **Связка (подтверждено):** Bybit P2P, одна фиат-валюта — купить USDT дешевле → продать USDT дороже; чистая маржа ≥ порога после комиссий и лимитов объявлений.
- Фильтр контрагентов: рейтинг, число сделок, чёрный список; пересечение методов оплаты объявления с доступными transfer-методами и с картами пула под эту валюту/страну.
- Каждая возможность сохраняется с входами расчёта (включая `currency` и методы) для воспроизводимости.

**FR-3. Исполнение сделок**

- Сделка = автомат состояний, например: `opportunity` → `awaiting_open_ack` → `buy_order` → `awaiting_pay_ack` → `mark_paid` → `awaiting_crypto` → `sell_order` → `awaiting_incoming` → `awaiting_release_ack` → `released` → `closed` (+ ветки cancel / dispute).
- Внешние вызовы к Bybit идемпотентны (ключ идемпотентности); повтор после сбоя не создаёт второй ордер.
- Тайм-ауты и автоотмена на шагах **до** отправки фиата. Шаг release по таймауту **не** отменяется автоматически: напоминания и эскалация оператору.

Подтверждение оператора (`operator_ack`):

- Контрольные точки: создание buy-ордера, отметка «я оплатил» / `mark_paid`, release на sell-ноге. В конфиге на каждую точку флаг `require_ack` (на старте все `true`).
- Перед выполнением подтверждённого шага — перепроверка цены/лимитов/статуса ордера; при потере выгоды шаг не выполняется, оператор уведомляется.
- Различать: **`operator_ack`** (кнопка), **`payment_matched`** (входящий перевод сверен), **`receipt`** (загруженное фото/скрин чека). Автоматического банк-матчинга нет.

**FR-4. Платежи (ручные) и инструменты**

- Исходящие: Mini App показывает реквизиты продавца из ордера Bybit; оператор переводит вручную с выбранного `payment_instrument` (карта пула); **обязательно загружает фото чека**; затем «я оплатил» → `mark_paid` на Bybit (и при необходимости отправка чека контрагенту через чат API).
- Входящие: система показывает сумму, валюту, на какой инструмент ждать перевод; оператор сверяет в банке, **загружает чек/скрин зачисления**, жмёт `payment_matched` → затем `operator_ack` на release.
- Справочник `payment_instrument`: страна (KZ, GE, TJ, UZ, KG, …), валюта, тип метода (карта / иное transfer), маска реквизита, активен/нет, лимиты. Без банковского API.
- Чеки хранятся как файлы (объектное хранилище или диск VPS) + метаданные в БД; в аудите — кто загрузил и к какому deal/payment.

**FR-5. Риск-менеджмент**

- Лимиты: размер сделки, число открытых сделок, суммарная экспозиция, дневной убыток, частота исходящих переводов.
- Kill switch: стоп новых сделок по команде и по триггерам (аномальный убыток, серия ошибок API, расхождение балансов с Bybit).
- Поведение kill switch для открытых: новые `operator_ack` на открытие запрещены; неоплаченные ордера — предложить/выполнить cancel; ордера после оплаты / awaiting release — не трогать автоматически, только алерт оператору.
- Режимы: `dry-run` → `paper` → `live+confirm` → (позже) `live` с выборочным снятием `require_ack`.

**FR-6. Балансы и инвентарь**

- Остатки USDT на Bybit (funding/spot — как потребует API) и учёт фиата по валютам (RUB/EUR/USD/KZT) «на картах» — вручную оператором или из леджера; предупреждение о нехватке нужной валюты для ноги сделки.

**FR-7. Учёт и отчёты**

- Леджер двойной записью: сделка, комиссии, фиатные ноги (как события, подтверждённые оператором).
- P&L по сделке, дню, связке; выгрузка CSV.

**FR-8. Telegram: Mini App + бот**

- **Mini App (основной интерфейс):** дашборд (режим, балансы, P&L), связки, сделки с реквизитами и чеками, **чат с контрагентом по ордеру**, очередь подтверждений, справочник карт/инструментов, лимиты/режимы, аудит, споры.
- Подтверждение шага: карточка (сумма, курс, контрагент, маржа, реквизиты, выбранный инструмент, TTL, превью чека) — «подтвердить» / «отклонить».
- Чат: лента сообщений Bybit P2P в реальном времени (poll или push, как позволит API); отправка текста; вложение чека в переписку, если API поддерживает.
- Реалтайм UI: WebSocket или SSE. HTTPS. Auth: подпись `initData` + whitelist Telegram user id.
- **Бот:** пуши (связка, ждёт подтверждения + deep link в Mini App, новое сообщение в чате, ошибка, спор, лимит, kill switch) и команды: статус, start/stop, kill switch. Опасные — доп. подтверждение.

**FR-9. Конфигурация и аудит**

- Параметры стратегии и лимитов версионируются; изменения — в аудит.
- Аудит решений и внешних вызовов append-only.

**FR-10. Точка подключения ИИ-агентов (задел, агенты позже)**

- Tool-API только на чтение и на предложения изменений конфига; без доступа к ключам и прямым вызовам биржи; те же лимиты и аудит.

## 5. Нефункциональные требования

Корректность денег важнее скорости.

| Область | Требование |
| --- | --- |
| Корректность денег | Только `Decimal` / `NUMERIC`, без `float`; идемпотентность; леджер append-only |
| Устойчивость | Состояние сделки в PostgreSQL; после рестарта — продолжение с последнего зафиксированного шага |
| Сверка | Не реже раза в сутки и после рестарта: ордера/балансы в системе ↔ Bybit; расхождение → алерт + стоп новых сделок |
| Скорость | До карточки в Mini App — секунды; далее — оператор |
| Доступность | Uptime ядра ориентир 99%/мес; ответ оператора в SLA не входит |
| Наблюдаемость | structlog, базовые метрики, алерты в Telegram (Prometheus/Grafana — по желанию после live) |
| Безопасность | Раздел 10 |
| Тестируемость | Симулятор Bybit для `paper`; автотесты FSM, маржи, идемпотентности |
| Воспроизводимость | Решение восстанавливается по снимкам входов + версии конфига |
| Сопровождение | Alembic-миграции, деплой одной командой (Compose), runbook |

## 6. Архитектура и жизненный цикл сделки

Внешний мир (Bybit, Telegram) — через адаптеры; ядро биржу не знает. Добавление второй биржи позже = новый адаптер без переписывания FSM.

**Архитектура (логическая):**

```text
[Bybit P2P/Spot API]     [Telegram Bot API]
         │                        │
    ExchangeAdapter          TelegramAdapter
         │                        │
         └──────────┬─────────────┘
                    ▼
        Core: opportunity · deal FSM · risk · ledger
                    │
        PostgreSQL · (Redis) · Mini App (React) ← FastAPI
```

**Жизненный цикл (упрощённо):**

```text
связка найдена
    → карточка open в Mini App (TTL из конфига)
    → operator_ack → create buy order
    → реквизиты продавца + чат в Mini App
    → перевод вручную с карты пула → загрузка фото чека
    → operator_ack «оплатил» → mark_paid (+ чек в чат при поддержке API)
    → ждём USDT
    → create sell order (с ack, если флаг) + указать наш payment_instrument
    → входящий перевод → фото чека зачисления → payment_matched
    → operator_ack → release
    → closed / P&L
```

Каждый шаг: запись в БД **до и после** внешнего вызова. До оплаты таймаут → cancel. `mark_paid` и release без обязательного чека / `payment_matched` — запрещены правилами приёмки.

## 7. Технологический стек

Python 3 + asyncio, PostgreSQL, Redis, aiogram, Mini App на React, деплой Docker Compose.

| Слой | Выбор | Почему | Альтернатива |
| --- | --- | --- | --- |
| Язык | Python 3.12, asyncio | Скорость разработки, экосистема | Go / TypeScript |
| API | FastAPI | REST + WS/SSE для Mini App, health | Другой ASGI |
| Telegram | aiogram 3 | Уведомления и команды | python-telegram-bot |
| HTTP | httpx, tenacity, aiolimiter | Таймауты и rate limit | aiohttp |
| БД | PostgreSQL 16, SQLAlchemy 2, Alembic | ACID, JSONB сырых ответов | — |
| Кэш / очереди | Redis 7 + arq | Блокировки, фоновые задачи | Только Postgres на старте |
| Оркестрация | FSM в PostgreSQL + outbox | Прозрачность для одного оператора | Temporal |
| Деньги | `Decimal`, `NUMERIC` (крипта до 18 знаков; фиат — 2–4) | Без ошибок float | — |
| Наблюдаемость | structlog; Sentry по желанию | Алерты в TG | + Prometheus позже |
| Секреты | env / SOPS+age на VPS | Не в git | Vault |
| Деплой | Docker Compose на VPS, CI по желанию | Один оператор | k8s не нужен |
| Тесты | pytest, recorded HTTP, симулятор Bybit | Paper = тот же код | — |
| Mini App | React + TypeScript + Vite + Telegram WebApp SDK + TanStack Query | Требование: UI в Mini App | Vue / Svelte |

**Bybit:** P2P-клиент пишется по [официальной P2P API-документации](https://bybit-exchange.github.io/docs/p2p/guide); ccxt — только если понадобится спот/баланс, не как замена P2P.

**Протокол адаптера (MVP + запас на вторую биржу):**

```python
class P2PExchange(Protocol):
    async def list_ads(self, query: AdQuery) -> list[Ad]: ...
    async def list_payment_methods(self, currency: str) -> list[PaymentMethod]: ...
    async def create_order(self, ad: Ad, amount: Decimal, key: str) -> Order: ...
    async def get_order(self, order_id: str) -> Order: ...
    async def get_order_payment_info(self, order_id: str) -> PaymentDetails: ...
    async def mark_paid(self, order_id: str) -> None: ...
    async def release(self, order_id: str) -> None: ...
    async def cancel(self, order_id: str) -> None: ...
    async def get_balances(self) -> dict[str, Decimal]: ...
    async def get_chat_messages(self, order_id: str) -> list[ChatMessage]: ...
    async def send_chat_message(self, order_id: str, text: str) -> None: ...
    async def send_chat_attachment(self, order_id: str, file: bytes, mime: str) -> None: ...
    # dispute — по мере поддержки API / этапа 3
```

## 8. Интеграции

| Интеграция | Назначение | Что проверить на этапе 0 |
| --- | --- | --- |
| Bybit P2P API | Объявления, методы оплаты, ордера, реквизиты, mark_paid, release, cancel, **чат** | Ключ P2P без withdraw; chat/upload в API; IP whitelist |
| Bybit Spot/Wallet API | Балансы USDT | Read-only / те же ключи |
| Telegram Bot + Mini App | UI, чат, чеки, подтверждения, пуши | HTTPS Mini App; whitelist; лимиты размера вложений |
| Карты пула (KZ/GE/TJ/UZ/KG/…) | Ручные переводы | Нет API банка; только справочник + чеки |

Только официальный API. Скрейпинг и браузерная автоматизация запрещены.

**Почему Bybit:** открытая P2P API-дока + уже есть аккаунт с General Advertiser. Bitget/OKX — выше порог merchant; HTX — запасной адаптер позже.

## 9. Модель данных

**Соглашения схемы:** таблицы singular; PK — `integer` (не UUID); время — `timestamptz` UTC; деньги — только `NUMERIC` (crypto 38,18 / fiat 24,4 / price 24,8 / pct 12,6); enum-значения — `VARCHAR` + `CHECK`; FK — `ON DELETE RESTRICT`. Подробно: [zdocs/db/сущности.md](../db/сущности.md).

| Сущность | Ключевые поля |
| --- | --- |
| `exchange_account` | площадка=`bybit`, `secret_ref`, права (без withdraw), режим |
| `counterparty` | id на Bybit, ник, рейтинг, сделок, blacklist |
| `ad_snapshot` | `token=USDT`, `currency`, сторона, цена, лимиты, методы, контрагент, `captured_at`, raw (**append-only**) |
| `config_version` | `version`, `params` JSONB (лимиты, порог маржи, `require_ack`), автор (**append-only**) |
| `opportunity` | валюта связки, buy/sell срезы, расчёт маржи, версия конфига, решение |
| `payment_instrument` | страна, валюта, тип метода, маска реквизита, label, активен, лимиты |
| `deal` | `currency`, состояние FSM, плановая/фактическая маржа, `state_deadline_at`, `row_version` |
| `order_leg` | внешний id Bybit, сторона, суммы/цена, `currency`, статус, `idempotency_key` |
| `payment` | направление in/out, `currency`, инструмент, маска реквизитов, сумма, статус, связь с ордером |
| `receipt` | deal/payment, `storage_key`, mime, size, `sha256`, кто загрузил, сторона out/in (**append-only**) |
| `chat_message` | `order_leg_id`, direction, text/attachment, время, raw (**append-only**) |
| `operator_action` | deal_id, шаг, ack/reject, telegram user id, context (**append-only**) |
| `balance_snapshot` | источник (bybit / manual_fiat), актив, сумма, время |
| `ledger_entry` | `transaction_id`, дебет, кредит, сумма > 0, актив, deal/payment (**append-only**) |
| `audit_event` | актор, действие, entity_type/id, input/result JSONB (**append-only**) |
| `exchange_call` | аккаунт, deal/leg (nullable), `operation`, `idempotency_key` UK, status, request/response — идемпотентность Bybit шире, чем ключ на `order_leg` |
| `agent_proposal` | (задел) роль агента, proposal, статус, результат |

**Составные FK (согласованность валюты/сделки):**

| Код | Родитель → потомок |
| --- | --- |
| C1 | `deal(id, currency)` → `order_leg(deal_id, currency)` |
| C2 | `opportunity(id, currency)` → `deal(opportunity_id, currency)` |
| C3 | `ad_snapshot(id, currency)` → opportunity buy/sell и `order_leg.ad_snapshot_id` |
| C4 | `order_leg(id, deal_id, currency)` → `payment(…)` |
| C5 | `payment_instrument(id, currency)` → `payment(…)` |
| C6 | `payment(id, deal_id, direction)` → `receipt(…, side)` |
| C7 | `payment(id, deal_id)` → `ledger_entry(…)` |

**Append-only на уровне БД** (функция/триггер `forbid_mutation`, UPDATE/DELETE запрещены):  
`ad_snapshot`, `config_version`, `operator_action`, `ledger_entry`, `audit_event`, `receipt`, `chat_message`.  
`exchange_call` **не** append-only: строка обновляется после ответа API (`started` → `succeeded`/`failed`/`unknown`).

**Принципы:** idempotency keys на вызовы Bybit (`order_leg` + `exchange_call`); деньги только `NUMERIC`; raw API в JSONB; доказательства (чек, чат, леджер, аудит) не переписываются.

## 10. Безопасность и эксплуатация

- Ключи Bybit: **без withdraw**, IP whitelist VPS, по возможности раздельные read / trade.
- Секреты вне git.
- Mini App + бот: whitelist Telegram ID; опасные действия — повторное подтверждение; всё в аудит.
- Чеки и маски карт: доступ только оператору; не светить полные реквизиты в логах; срок хранения чеков — в конфиге.
- Лестница режимов: `dry-run` → `paper` → `live+confirm` → `live`; только вручную вверх.
- Kill switch — см. FR-5.
- Бэкап PostgreSQL ежедневно + проверка restore.
- Алерты в Telegram: ошибки API, зависшие сделки, расхождения сверки.
- Runbook: «перевёл, mark_paid не прошёл»; «деньги на карту пришли, ордер не найден»; «оператор не ответил до TTL».
- SSH по ключу, минимум открытых портов (HTTPS + SSH).

## 11. Этапы реализации и критерии приёмки

Сроки — после создания API-ключа и первичных лимитов (вопрос 3).

| Этап | Содержание | Критерий перехода |
| --- | --- | --- |
| 0. Разведка | P2P API-ключ + IP whitelist; список transfer-методов по валютам; проверка chat/attachment API; Mini App HTTPS | Успешные `list_ads`, методы оплаты, балансы; зафиксировано, есть ли чат/вложения в API |
| 1. Данные и сигналы | Сбор по RUB/EUR/USD/KZT, маржа, список в Mini App / пуш | Ненулевая чистая маржа хотя бы по одной валюте |
| 2. Paper | FSM + подтверждения + загрузка чеков + чат (симулятор) + леджер + справочник карт | Сходимость леджера; рестарт без дублей; чек обязателен на pay/release |
| 3. live+confirm | Мелкие сделки, карты пула, чат с контрагентом, споры вручную | Серия сделок без расхождений с Bybit |

| 4. Рост | Лимиты вверх; точечное снятие `require_ack`; maker / вторая биржа — по решению | Решение оператора |

**Общие критерии приёмки:**

- `mark_paid` невозможен без загруженного исходящего чека; release — без входящего чека, `payment_matched` и `operator_ack` (пока флаг включён).
- Повтор обработки события не создаёт дублей ордеров / `mark_paid`.
- Сверка леджера с Bybit проходит на контрольной выборке сделок.
- Kill switch за секунды стопает новые сделки и пишет в Telegram.
- Любая сделка восстанавливается по аудиту: что увидели, что решили, кто подтвердил.

## 12. Подключение ИИ-агентов

Агенты — ограниченные пользователи ядра: читают и предлагают; деньги двигает только детерминированная логика + оператор.

| Роль | Что может | Кто подтверждает |
| --- | --- | --- |
| Аналитик | Сделки, срезы, отчёты, сводки | Не требуется |
| Советник | Предложения по лимитам / порогу маржи, разбор спора | Оператор в Mini App |
| Исполнитель (позже) | Узкий whitelist действий | Лимиты ядра + kill switch |

- Отдельный токен/роль; секретов Bybit не видит.
- Не обходит kill switch и `require_ack`.
- Текст чата/объявлений — недоверенный (anti prompt injection).
- Лимиты частоты/стоимости LLM; журнал в аудите.
- Сущность `agent_proposal`: предложено / принято / отклонено.
