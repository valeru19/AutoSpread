# Сущности БД AutoSpread

Документ описывает **фактическую** схему PostgreSQL (миграция `0001_initial_schema`): зачем нужна каждая таблица, ключевые поля, с кем связана и в каких сценариях участвует.

Связанные материалы: [ТЗ §9](../tz/техническое-задание.md), ORM [`backend/app/models/`](../../backend/app/models/).

---

## 1. Общие правила схемы

| Правило | Как сделано |
| --- | --- |
| Имена таблиц | Singular: `deal`, не `deals` |
| Первичный ключ | `id` — `integer` IDENTITY (не UUID) |
| Время | `timestamptz`, UTC |
| Деньги | Только `NUMERIC`: crypto `(38,18)`, fiat `(24,4)`, price `(24,8)`, pct `(12,6)` — без `float` |
| Перечисления | `VARCHAR` + `CHECK`, не native Postgres ENUM |
| Удаление по FK | Везде `ON DELETE RESTRICT` |
| Append-only | Таблицы с триггером `forbid_mutation`: нельзя `UPDATE`/`DELETE` |
| Сырые ответы API | JSONB (`raw`, `request`/`response`) |
| Секреты и полные карты | В БД не хранятся: `secret_ref`, `masked_details`, файл чека вне БД |

**Append-only таблицы:** `ad_snapshot`, `config_version`, `operator_action`, `ledger_entry`, `audit_event`, `receipt`, `chat_message`.

**TTL (не колонки схемы, а env):** `ADS_TTL_DAYS=90`, `RECEIPT_TTL_DAYS=1825` — для будущих cleanup-job.

### Составные внешние ключи (C1–C7)

Защищают согласованность валюты и принадлежности к сделке:

| Код | Родитель | Потомок |
| --- | --- | --- |
| C1 | `deal(id, currency)` | `order_leg(deal_id, currency)` |
| C2 | `opportunity(id, currency)` | `deal(opportunity_id, currency)` |
| C3 | `ad_snapshot(id, currency)` | `opportunity` (buy/sell), `order_leg.ad_snapshot_id` |
| C4 | `order_leg(id, deal_id, currency)` | `payment(order_leg_id, deal_id, currency)` |
| C5 | `payment_instrument(id, currency)` | `payment(payment_instrument_id, currency)` |
| C6 | `payment(id, deal_id, direction)` | `receipt(payment_id, deal_id, side)` |
| C7 | `payment(id, deal_id)` | `ledger_entry(payment_id, deal_id)` |

## 2. Карта взаимодействий (жизненный цикл)

```text
config_version ─────────────────────────────┐
                                            ▼
exchange_account          counterparty
       │                       │
       │                  ad_snapshot (buy / sell)
       │                       │
       │                       ▼
       │                 opportunity ──► deal ◄── operator_action
       │                       │           │
       │                       │           ├── order_leg (buy)
       │                       │           │      ├── payment (out) ──► receipt
       │                       │           │      ├── chat_message
       │                       │           │      └── exchange_call
       │                       │           │
       │                       │           └── order_leg (sell)
       │                       │                  ├── payment (in) ──► receipt
       │                       │                  ├── chat_message
       │                       │                  └── exchange_call
       │                       │
       ▼                       ▼
balance_snapshot          ledger_entry
                               │
                          audit_event (везде)

agent_proposal — задел под ИИ, пока слабо связан с остальным
payment_instrument — карты/методы оператора для out и manual_fiat
```

Типичный поток одной арбитражной сделки:

1. Воркер пишет срезы рынка → `ad_snapshot` + обновляет/создаёт `counterparty`.
2. Скоринг считает связку → `opportunity` (ссылки на два среза + `config_version`).
3. При «берём» → `deal` в состоянии FSM; шаги с подтверждением → `operator_action`.
4. Открытие ног → `order_leg` + запись в `exchange_call` до/после Bybit.
5. Фиат наружу/внутрь → `payment`, доказательства → `receipt`, переписка → `chat_message`.
6. Движение активов → `ledger_entry`; решения и переходы → `audit_event`.
7. Периодически → `balance_snapshot` для сверки.

## 3. Справочники и конфигурация

### 3.1. `exchange_account`

**Зачем.** Учёт биржевого аккаунта, которым система торгует. Сами API-ключи в БД не лежат — только имя секрета в окружении (`secret_ref`).

**Для чего.** Привязка ордеров, балансов и вызовов API к конкретному аккаунту и режиму работы (`dry_run` / `paper` / `live_confirm` / `live`).

**Ключевые поля:** `exchange` (`bybit`), `label`, `secret_ref`, `permissions` (JSONB), `mode`, `is_active`.

**Ограничения:** UK `(exchange, label)`; CHECK — `withdraw` в `permissions` не может быть `true`.

**С кем связана:**

- ← `order_leg`, `exchange_call`, `balance_snapshot` (источник bybit)

---

### 3.2. `counterparty`

**Зачем.** Кэш профиля контрагента на P2P (ник, рейтинг, статистика), чтобы не дергать API на каждый срез и быстро фильтровать риск.

**Для чего.** Связь объявлений и ордеров с человеком/мерчантом; blacklist при повторных проблемах.

**Ключевые поля:** `exchange`, `external_id`, `nickname`, `rating`, `orders_count`, `completion_rate`, `is_blacklisted`, `blacklist_reason`, `last_seen_at`.

**Ограничения:** UK `(exchange, external_id)`.

**С кем связана:**

- ← `ad_snapshot`, `order_leg`

---

### 3.3. `payment_instrument`

**Зачем.** Справочник **наших** способов оплаты (карта/счёт пула), которыми оператор платит или принимает фиат вручную.

**Для чего.** Выбор инструмента в карточке Mini App, лимиты на транзакцию/сутки, маскирование реквизитов в UI и логах.

**Ключевые поля:** `country_code`, `currency`, `method_code`, `label`, `masked_details`, `is_active`, `per_tx_limit`, `daily_limit_amount`, `daily_limit_count`.

**Ограничения:** UK `(id, currency)` для составного FK C5.

**С кем связана:**

- ← `payment` (обычно исходящий платёж)
- ← `balance_snapshot` при `source = manual_fiat`

---

### 3.4. `config_version`

**Зачем.** Неизменяемый снимок параметров риска и UX (порог маржи, лимиты, флаги `require_ack`, TTL шагов). Любое изменение конфига = **новая** строка с большим `version`.

**Для чего.** Воспроизводимость: сделка и opportunity помнят, при каких правилах их посчитали и вели. Аудит «кто поменял политику».

**Ключевые поля:** `version` (UK, > 0), `params` (JSONB), `created_by`, `comment`.

**Режим:** **append-only** (триггер).

**С кем связана:**

- ← `opportunity`, `deal`

Начальная запись создаётся скриптом `scripts.seed_config_version`, не миграцией.

---

## 4. Рынок и отбор связок

### 4.1. `ad_snapshot`

**Зачем.** Неизменяемый **срез** чужого P2P-объявления на момент опроса API. Рынок меняется — история цен нужна для расчёта и разбора споров.

**Для чего.** Вход для скоринга связок; ссылка из opportunity и (опционально) из order_leg на объявление, с которым работали.

**Ключевые поля:** `exchange`, `external_ad_id`, `token` (USDT), `currency`, `side` (buy/sell), `price`, `available_amount`, `min_amount`, `max_amount`, `payment_methods` (JSONB), `counterparty_id`, `captured_at`, `raw`.

**Режим:** **append-only**. Хранение ограничивается TTL (`ADS_TTL_DAYS`), не партициями.

**С кем связана:**

- → `counterparty`
- ← `opportunity` (buy и sell, разные id, CHECK buy ≠ sell)
- ← `order_leg.ad_snapshot_id` (nullable)

---

### 4.2. `opportunity`

**Зачем.** Результат расчёта одной арбитражной **связки**: купить по одному объявлению, продать по другому, в одной фиат-валюте.

**Для чего.** Фиксация цифр маржи/комиссий/входов калькулятора и решения (`taken` / `skipped` / `expired`). Если взяли — из неё рождается ровно одна `deal` (UK по `opportunity_id`).

**Ключевые поля:** `currency`, `buy_ad_snapshot_id`, `sell_ad_snapshot_id`, `amount_token`, `buy_price`, `sell_price`, `gross_margin_pct`, `net_margin_pct`, `net_profit_fiat`, `fees`, `calc_inputs`, `config_version_id`, `decision`, `decision_reason`.

**С кем связана:**

- → `ad_snapshot` ×2, `config_version`
- ← `deal` (1:1 по opportunity)

---

## 5. Сделка и исполнение

### 5.1. `deal`

**Зачем.** Центральная сущность исполнения: одна взятая opportunity в виде **автомата состояний** (FSM) до closed / cancelled / dispute.

**Для чего.** Хранит валюту связки, режим, плановую и фактическую прибыль, дедлайн текущего шага (`state_deadline_at`), версию строки (`row_version` для оптимистичной блокировки), причину отмены.

**Ключевые поля:** `opportunity_id`, `currency`, `state`, `mode`, `amount_token`, `planned_margin_pct`, `planned_profit_fiat`, `actual_profit_fiat`, `config_version_id`, `state_deadline_at`, `cancel_reason`, `row_version`, `closed_at`.

**Индексы:** по `state`; частичный `ix_deal_open_states` для незакрытых.

**С кем связана:**

- → `opportunity` (C2), `config_version`
- ← `order_leg`, `payment`, `receipt`, `operator_action`, `ledger_entry`, `exchange_call`, (логически) `audit_event`

Состояния FSM (CHECK):  
`opportunity` → `awaiting_open_ack` → `buy_order` → `awaiting_pay_ack` → `mark_paid` → `awaiting_crypto` → `sell_order` → `awaiting_incoming` → `awaiting_release_ack` → `released` → `closed`, плюс `cancelled`, `dispute`.

---

### 5.2. `order_leg`

**Зачем.** Одна **нога** сделки на бирже: покупка или продажа USDT в P2P. У сделки обычно две ноги с UK `(deal_id, side)`.

**Для чего.** Идемпотентное создание ордера (`idempotency_key`), статус жизненного цикла на Bybit, связь с контрагентом и срезом объявления, сырой ответ API.

**Ключевые поля:** `deal_id`, `exchange_account_id`, `side`, `external_order_id`, `currency`, `amount_token`, `price`, `amount_fiat`, `status`, `counterparty_id`, `ad_snapshot_id`, `idempotency_key`, `raw`.

**Ограничения:** UK `idempotency_key`; частичный UK `(exchange_account_id, external_order_id)` где external не NULL; C1 с deal; C3 с ad_snapshot.

**С кем связана:**

- → `deal`, `exchange_account`, `counterparty`, `ad_snapshot?`
- ← `payment`, `chat_message`, `exchange_call`

---

### 5.3. `payment`

**Зачем.** Учёт **фиатного** платежа по ноге: мы платим контрагенту (`out`) или ждём/фиксируем входящий (`in`). Автоматического банк-матчинга нет — статусы выставляет оператор/система по правилам ТЗ.

**Для чего.** Связка суммы, валюты, инструмента оплаты, маски реквизитов контрагента и статусов (`pending` → `sent` → `matched` / `failed` / `cancelled`).

**Ключевые поля:** `deal_id`, `order_leg_id`, `direction`, `currency`, `amount`, `payment_instrument_id?`, `counterparty_requisites_masked`, `status`, `operator_marked_at`, `matched_at`.

**С кем связана:**

- → `deal`, `order_leg` (C4), `payment_instrument?` (C5)
- ← `receipt` (C6), `ledger_entry` (C7)

---

### 5.4. `receipt`

**Зачем.** Метаданные **файла-доказательства** оплаты (фото/скрин). Сам файл — на диске/S3 (`storage_key`), в БД нет бинарного содержимого.

**Для чего.** Привязка чека к сделке и (если есть) к платежу той же стороны (`side` = `out`/`in` согласован с `payment.direction` через C6); целостность файла (`sha256`), кто загрузил.

**Ключевые поля:** `deal_id`, `payment_id?`, `side`, `storage_key`, `mime`, `size_bytes`, `sha256`, `uploaded_by`.

**Режим:** **append-only** (доказательство + контроль `sha256` — строку нельзя подменить).  
Чек вставляется сразу с `payment_id`; UPDATE и DELETE запрещены триггером; если платежа ещё нет, сначала создаётся `payment` со статусом `pending`.

**TTL:** `RECEIPT_TTL_DAYS` (по умолчанию 5 лет — практика AML/финтех).

**С кем связана:**

- → `deal`, `payment?`

---

### 5.5. `chat_message`

**Зачем.** История переписки по ордеру P2P (входящие/исходящие/системные), чтобы оператор и аудит видели контекст спора без повторной выгрузки из Bybit.

**Для чего.** Хранение текста/вложений (метаданные attachment в JSONB) и raw API; дедуп по `external_message_id` в рамках ноги.

**Ключевые поля:** `order_leg_id`, `external_message_id?`, `direction` (`in`/`out`/`system`), колонка БД `text` (в ORM: `message_text`), `attachment`, `sent_at`, `raw`.

**Режим:** **append-only** (спорная переписка не редактируется; новые сообщения — только INSERT).  
Дедупликация только через `ON CONFLICT DO NOTHING`.

**С кем связана:**

- → `order_leg`

---

### 5.6. `operator_action`

**Зачем.** Неизменяемый журнал нажатий оператора в Mini App / боте: подтвердил или отклонил шаг FSM.

**Для чего.** Доказательство human-in-the-loop; в `context` — снимок цены/лимитов/статуса на момент решения (чтобы потом не спорить «что он видел»).

**Ключевые поля:** `deal_id`, `step` (`open`/`pay`/`mark_paid`/`release`/`cancel`/`payment_matched`), `action` (`ack`/`reject`), `telegram_user_id`, `context` (JSONB).

**Режим:** **append-only**.

**С кем связана:**

- → `deal`

---

### 5.7. `exchange_call`

**Зачем.** Журнал **идемпотентных** вызовов Bybit шире, чем один `order_leg.idempotency_key`: `mark_paid`, `release`, `cancel`, чат, балансы и т.д.

**Для чего.** Запись «до» (`status=started`, `request`) и «после» (`succeeded`/`failed`/`unknown`, `response`, `finished_at`); защита от двойного клика и ретраев.

**Ключевые поля:** `exchange_account_id`, `deal_id?`, `order_leg_id?`, `operation`, `idempotency_key` (UK), `status`, `request`, `response?`, `finished_at?`.

**С кем связана:**

- → `exchange_account`, `deal?`, `order_leg?`

Строки **можно** обновлять (смена статуса после ответа API) — это не append-only таблица.

---

## 6. Учёт, балансы, аудит

### 6.1. `balance_snapshot`

**Зачем.** Периодический снимок остатка: USDT на Bybit или фиат «в голове»/на карте пула (ручной учёт).

**Для чего.** Сверка с леджером, алерты «деньги не там», отчёты по экспозиции.

**Ключевые поля:** `source` (`bybit` | `manual_fiat`), `asset`, `amount`, `exchange_account_id?`, `payment_instrument_id?`, `captured_at`.

**Ограничение:** ровно одна ссылка по типу источника (bybit → только exchange_account; manual_fiat → только payment_instrument).

---

### 6.2. `ledger_entry`

**Зачем.** Бухгалтерская **двойная запись** в одной строке: `debit_account` ← `credit_account` на `amount` актива. История денег не переписывается.

**Для чего.** P&L, комиссии, перемещения между `bybit:usdt`, `fiat:…`, `fees:bybit`, `pnl` и т.п.; привязка к сделке и опционально к платежу.

**Ключевые поля:** `transaction_id` (UUID, группирует строки одной операции), `debit_account`, `credit_account`, `amount` (> 0), `asset`, `deal_id?`, `payment_id?`, `description`.

**Режим:** **append-only**.  
CHECK: если указан `payment_id`, обязан быть `deal_id` (C7).

---

### 6.3. `audit_event`

**Зачем.** Универсальный append-only лог решений системы, оператора и (позже) агентов: что сделали, над чем, с каким входом/результатом.

**Для чего.** Разбор инцидентов, compliance, трассировка переходов FSM и внешних эффектов без изменения исходных сущностей.

**Ключевые поля:** `actor_type` (`system`/`operator`/`agent`), `actor_id`, `action`, `entity_type`, `entity_id?` (полиморфная ссылка без FK), `input`, `result` (JSONB).

**Режим:** **append-only**.  
Индексы: `(entity_type, entity_id)`, `created_at`.

---

## 7. Задел под ИИ

### 7.1. `agent_proposal`

**Зачем.** Место для предложений ИИ-агентов (аналитик / советник / исполнитель) до того, как они смогут писать в боевые таблицы напрямую.

**Для чего.** Человек или политика принимает/отклоняет (`status`, `decided_by`, `decided_at`); тело предложения и итог — в JSONB.

**Ключевые поля:** `agent_role`, `proposal`, `status`, `decided_by?`, `decided_at?`, `result?`.

**Связи:** пока без жёстких FK на deal — намеренно слабо связано, чтобы не блокировать эволюцию агентов.

## 8. Сводная таблица

| Сущность | Роль одной фразой | Append-only | Главные соседи |
| --- | --- | --- | --- |
| `exchange_account` | Наш аккаунт Bybit | нет | order_leg, exchange_call, balance_snapshot |
| `counterparty` | Контрагент P2P | нет | ad_snapshot, order_leg |
| `payment_instrument` | Наша карта/метод | нет | payment, balance_snapshot |
| `config_version` | Снимок политики | **да** | opportunity, deal |
| `ad_snapshot` | Срез объявления | **да** | counterparty, opportunity, order_leg |
| `opportunity` | Расчёт связки | нет | ad_snapshot×2, config, deal |
| `deal` | FSM сделки | нет | opportunity, ноги, платежи, ack |
| `order_leg` | Нога buy/sell | нет | deal, account, payment, chat |
| `payment` | Фиат in/out | нет | order_leg, instrument, receipt, ledger |
| `receipt` | Метаданные чека | **да** | deal, payment |
| `chat_message` | Чат по ордеру | **да** | order_leg |
| `operator_action` | Ack/reject шага | **да** | deal |
| `exchange_call` | Идемпотентный API-вызов | нет | account, deal?, leg? |
| `balance_snapshot` | Срез баланса | нет | account или instrument |
| `ledger_entry` | Двойная запись | **да** | deal?, payment? |
| `audit_event` | Журнал действий | **да** | полиморфно |
| `agent_proposal` | Предложение ИИ | нет | — |

## 9. Что сознательно не в БД

- Полные номера карт и секреты API  
- Байты чеков (только `storage_key` + hash)  
- Очереди/локи (Redis)  
- Сессии Telegram / JWT  

При изменении схемы этот файл нужно обновлять вместе с миграцией и `backend/app/models/README.md`.
