# Правила написания комментариев в коде

Этот документ описывает, когда и как комментировать код в проекте. Он основан на статье
[«Правила и рекомендации по комментированию в коде»](https://habr.com/ru/articles/645049/)
(Хабр, компания Docsvision, опирается на книгу Роберта Мартина «Чистый код») и дополнен общепринятыми
практиками из других источников (список в конце).

Это рекомендации, а не аксиомы: у команды может быть свой стандарт, и он приоритетнее.

## 1. Главный принцип

> **Комментарий отвечает на вопрос «зачем?», а не «что?».**

Что делает код, показывает сам код. Чего он показать не может — почему выбрано именно такое решение,
какое бизнес-требование за ним стоит, что сломается при «очевидном» улучшении.

Порядок действий:

1. Сначала сделайте код понятным: хорошие имена переменных, функций и классов, небольшие функции.
2. Если после этого остался вопрос «почему так?» — напишите комментарий.
3. Если хочется написать над функцией, что она делает, — лучше превратить этот текст в её название.

Комментарий не исправляет плохой код. Плохой код нужно переписать, а не объяснять.
Код со временем меняется, комментарии часто остаются прежними, поэтому каждый лишний комментарий — это
будущий источник ошибки.

## 2. Когда комментарий нужен

### 2.1. Объяснение намерения и неочевидного решения

Бизнес-требования порой приводят к решениям, которые без контекста выглядят странно. Комментарий
фиксирует причину. Он также помогает объяснить «магические числа» и особенности библиотек или браузеров.

```js
// Для дополнительных задач нужен префикс, чтобы id не совпал с id выездов
orderStateDTO.setOrderId("f_" + additionalTask.getId());
```

### 2.2. Сложные места: регулярные выражения, алгоритмы, формулы

Регулярное выражение с ходу не прочитать. Укажите формат, который оно разбирает.

```js
// Формат: kk:mm:ss EEE. MMM dd. yyyy
const timeMatcher = new RegExp('\\d*:\\d*:\\d* \\w*. \\w* \\d*. \\d*');
```

Если вы потратили время, чтобы разобраться в запутанном фрагменте, а на рефакторинг времени нет,
оставьте пояснение коллегам, чтобы им не пришлось повторять ваш путь.

### 2.3. Усиление важности

Комментарий защищает строку, которая выглядит лишней, но на самом деле необходима.

```js
// Вызов trim() важен: убирает начальные пробелы, иначе строка не распознается как список
let listItemContent = match.group(3).trim();
```

### 2.4. Предупреждение о последствиях

Предупредите того, кто будет менять код, чем это грозит.

```js
// Не уменьшать интервал ниже 500 мс — иначе ломается анимация с тулбаром в Safari
setInterval(() => { $(window).scrollTop(-1); resize(); }, 500);
```

### 2.5. Юридическая информация

Если стандарты компании или лицензия требуют, в начало файла помещают информацию об авторских правах и
лицензии. Это должна быть суть и ссылка на лицензию или внешний документ, а не трактат. Большинство
IDE умеют сворачивать такие блоки.

```js
/*
 * animate.css - https://daneden.github.io/animate.css/
 * Version - 3.7.2
 * Licensed under the MIT license - http://opensource.org/licenses/MIT
 *
 * Copyright (c) 2019 Daniel Eden
 */
```

### 2.6. Пометки о незавершённой работе

Честно отмечайте неполные реализации и известные ограничения. Это помогает следующему разработчику
(см. [раздел 5](#5-todo-и-другие-метки)).

### 2.7. Ссылки на внешние источники

Если решение опирается на спецификацию, issue, статью или обсуждение, оставьте ссылку.

## 3. Когда комментарий не нужен

### 3.1. Избыточные комментарии

Если комментарий повторяет то, что очевидно из кода, он только отнимает время.

```js
// ПЛОХО
// Если знаменатель равен 0, возвращается null
if (b == 0) {
    return null;
}
// результат метода
return a / b;
```

Проверка: если комментарий ничего не проясняет, удалите его.

### 3.2. Шум, бормотание, шутки

Эмоции и реакции разработчика не помогают понять код.

```js
// ПЛОХО
// WTF????? Refactor this!
// Не грусти, я тоже не понимаю, что здесь происходит :(
```

Если код непонятен, исправьте код или объясните, в чём именно сложность.

### 3.3. Журнальные комментарии и подписи авторов

Кто, когда и в рамках какой задачи менял строку, хранит система контроля версий. Комментарий быстро
становится недостоверным и вызывает сомнения у читающего.

```js
// ПЛОХО
// Добавлено Иваном
// Изменено в рамках задачи Task-675
// Поправлено 05.10.2019
```

Вместо этого пишите понятные сообщения коммитов.

### 3.4. Закомментированный код

Не оставляйте старый код в комментариях. Он не рефакторится вместе с окружением, устаревает, может не
компилироваться при раскомментировании, а коллеги боятся его удалять. Нужная версия всегда есть в Git.
Если важно объяснить, почему блок удалён, напишите это в сообщении коммита.

### 3.5. Позиционные маркеры

```js
// ПЛОХО
////////////////////////////////////////////////
************* Работа с заказами ****************
```

Желание визуально отделить блок кода — сигнал выделить его в отдельную функцию или модуль.

### 3.6. Комментарии у закрывающих скобок

```js
// ПЛОХО
try {
    while (condition) {
        // много строк
    } // while
    // много строк
} // try
```

При рефакторинге такие пометки «съезжают» и вводят в заблуждение. Современные IDE умеют сворачивать
блоки. Если блок настолько длинный, что нужна пометка, вынесите часть кода в отдельную функцию.

### 3.7. Недостоверные (устаревшие) комментарии

Неверная информация хуже её отсутствия. Если комментарий противоречит коду, он вредит.

### 3.8. Обязательные комментарии «для галочки»

Требование комментировать каждую функцию порождает мусор и не улучшает качество. Эффективнее требовать
хорошие имена функций и классов.

### 3.9. Не используйте комментарии для описания потоков и архитектуры

Комментарий видит только узкий контекст места, где он написан, и не может показать общую картину.
Общие схемы, потоки данных и архитектуру описывайте во внешней документации (README, ADR, диаграммы)
и ссылайтесь на неё из кода.

## 4. Как писать хороший комментарий

- **Пишите о причине, а не о механике.** «Используем Redis вместо памяти процесса, чтобы лимиты работали
  между инстансами» полезнее, чем «проверяем лимит».
- **Будьте краткими.** Длинные комментарии пропускают. Самое важное ставьте в начало.
- **Будьте точными.** Один комментарий — одна мысль, без двусмысленностей.
- **Не дублируйте код.** Не пересказывайте то, что видно по именам и логике.
- **Размещайте рядом с кодом**, к которому он относится, и придерживайтесь единого стиля.
- **Не комментируйте каждую строку.** Избыток комментариев ухудшает читаемость.
- **Пишите на языке, принятом в проекте**, и не смешивайте языки без необходимости.
- **Не оставляйте временные пометки без контекста**: «потом поправить» ничего не объясняет.
- **Улучшайте код вместо комментария**: переименуйте, вынесите функцию, замените магическое число константой.

Пример замены комментария названием:

```js
// ПЛОХО
// проверяет, что пользователь совершеннолетний
function check(u) { return u.age >= 18; }

// ХОРОШО
function isAdult(user) { return user.age >= 18; }
```

## 5. TODO и другие метки

TODO фиксирует, что нужно сделать не сейчас: рефакторинг, доработку после появления зависимой части и
т. п. Большинство IDE собирают такие метки в отдельное окно.

```js
// TODO: удалить после удаления класса GroupTaskPanel
// TODO: проверить логику при null во входном значении
```

Правила:

- Пишите **что** нужно сделать и **при каком условии**.
- По возможности указывайте ссылку на задачу в трекере.
- TODO — это технический долг. Периодически просматривайте их и удаляйте неактуальные.
- Не превращайте TODO в склад «когда-нибудь»: устаревшие метки так же вредны, как устаревшие комментарии.

## 6. Документирующие комментарии для API

Для публичного API используйте инструмент документирования языка (JSDoc, docstring, Javadoc, XML-doc и
т. д.). Такие комментарии показываются в подсказках IDE и попадают в сгенерированную документацию.

```js
/**
 * Складывает два числа.
 *
 * @param {number} first - первое слагаемое
 * @param {number} second - второе слагаемое
 * @returns {number} сумма
 */
function add(first, second) {
    return first + second;
}
```

Правила:

- Документируйте **только публичные** методы и классы. Приватные детали могут меняться без предупреждения
  и в общедоступную документацию не попадают.
- Описывайте параметры, возвращаемое значение, исключения и важные ограничения.
- Не пишите документацию, которая просто повторяет имя функции.

## 7. Поддержка актуальности

- **Обновляйте комментарий в том же коммите, что и код.**
- При изменении логики перечитывайте комментарии рядом.
- Если комментарий больше не нужен, удаляйте его.
- На код-ревью проверяйте не только код, но и комментарии: они не расходятся с реализацией?
- Не пишите комментарий заранее, а потом меняйте логику, забыв про него.

## 8. Чек-лист перед коммитом

- [ ] Нельзя ли сделать код понятным переименованием или выделением функции вместо комментария?
- [ ] Комментарий объясняет «почему», а не «что»?
- [ ] Он не повторяет очевидное из кода?
- [ ] Он актуален и соответствует текущей реализации?
- [ ] В нём нет шуток, эмоций, подписей авторов и дат правок?
- [ ] Нет закомментированного кода и позиционных маркеров?
- [ ] TODO содержит условие и (по возможности) ссылку на задачу?
- [ ] Для публичного API есть документирующий комментарий?
- [ ] Нет комментариев у закрывающих скобок?

## Краткая памятка

| Хорошо | Плохо |
|---|---|
| Объяснение намерения («почему») | Пересказ кода («что») |
| Пояснение regex и сложных алгоритмов | Шум, шутки, эмоции |
| Предупреждение о последствиях | Журнал изменений и авторы |
| Усиление важности неочевидной строки | Закомментированный код |
| TODO с условием и ссылкой на задачу | Позиционные маркеры и комментарии у `}` |
| Документация публичного API | Обязательные комментарии «для галочки» |
| Юридическая информация и лицензии | Устаревшие и недостоверные комментарии |

Хороший комментарий — тот, без которого удалось обойтись. А когда без него не обойтись, он должен
быть точным, кратким и актуальным.
